# Plan: Example conversation activity

## Goal

After this change, a person using the example app sees what the conversation is doing in plain English instead of a raw enum pair such as the lifecycle name joined to the activity name by a middle dot. The single live status line carries one fixed English sentence per state, and a small activity indicator next to the Start, Interrupt and Stop buttons shows an icon plus a short word for the same state, so the information is not carried by colour alone. Activity text appears only while this example believes its own session is capturing: before a successful Start, and after Stop, background, a fault or a system pause, a stale agent event can no longer overwrite the setup or stopped message. The library under `lib/` and the example session interface are untouched, and every status substring that existing tests depend on survives.

## Approach

The work lives entirely in the example. `example/lib/voice_screen_controller.dart` gains three pieces of state and one rule. The three pieces of state are a public `displayedActivity` field of type `TurnActivity` that defaults to idle, a public `activityPaused` boolean that defaults to false, and a private capture flag that records whether this controller believes the session it holds is capturing. The rule is that agent events may write the status line and the displayed activity only while the capture flag is true. `TurnActivity` is already visible to the example through the package import that the controller uses today, so no new import and no new type are needed.

The capture flag is owned by the controller and is set in exactly one place: the Start path, after the session's start call returns without throwing, while the epoch recorded before the call is still current and the session field is still the same object. It is cleared when Stop completes on a current epoch and the same session, when the app goes to the background, when the session is torn down or the controller is closed, when a fault event arrives, and when an event reports a suspended lifecycle. Interrupt never clears it, because an interrupt returns the turn to the microphone rather than ending capture. The epoch and identity guards already exist in the shared session runner and in the teardown helper, so the flag rides on checks the controller already performs rather than on new ones.

The Start wrapper currently passes its success sentence into the shared session runner and then asks the runner not to write it. That arrangement is why the listening sentence has never been seen. The shared runner is reshaped so that the three wrappers can each run their own controller-owned success step on the successful in-epoch same-session path, after the existing stale-completion branch that stops a session abandoned by a background event. That stale branch keeps returning before any status assignment, which is what protects the background message and the resume message that controller tests assert. On the successful Start path, the controller writes the listening sentence, sets `displayedActivity` to listening, clears `activityPaused`, and sets the capture flag. On the successful Interrupt path it writes the same listening sentence and sets `displayedActivity` to listening without touching the capture flag. On the successful Stop path it keeps today's stopped sentence, clears the capture flag, sets `displayedActivity` to idle and clears `activityPaused`.

The agent event handler loses the raw enum assignment. While the capture flag is true, a suspended lifecycle writes the paused sentence, sets `displayedActivity` to idle, sets `activityPaused` to true and clears the capture flag; any other non-fault event writes the fixed sentence for the event's activity, sets `displayedActivity` to that activity and clears `activityPaused`. While the capture flag is false, a non-fault event leaves the status, the displayed activity and the paused flag alone. A fault event keeps today's behaviour and stays unconditional: it writes the existing failure sentence, moves the phase to failed, sets `displayedActivity` to idle, clears `activityPaused` and clears the capture flag. Transcript and reply text keep updating on the events that carry them, exactly as now, because those fields are the user's own words and the agent's own reply rather than a claim about what the microphone is doing.

`example/lib/main.dart` gains one widget inside the existing conversation controls. The wrap that holds Start, Interrupt and Stop receives a fourth child keyed `activity-indicator`, containing an icon chosen for the current state and the short label for that state, wrapped in a semantics node that announces the same words. It is an addition, not a replacement: the three buttons keep their keys, their widget types and their enablement expressions, so Start remains a filled button that is disabled until setup has produced a session. The status text keeps its key and stays inside the existing live region, and every static sentence that the widget test searches for is left where it is.

## Why this approach

The research artifact considered three alternatives and rejected each. Replacing the three buttons with a single microphone control whose action follows the current activity was rejected because it hides the explicit interrupt control that the product documents, and because Start's enablement is stricter than Interrupt's and Stop's; collapsing them would also break the widget test that requires a disabled filled Start button before setup. Changing `lib/` so that the library publishes a listening event when start succeeds was rejected because it is a public behaviour change resting on native emission order that this work item deliberately did not read; the example can write its own sentence when its own call returns. Leaving the enum string was rejected because that string is the defect.

Within the chosen approach, two narrower alternatives were also rejected. Deriving the sentence from the event's lifecycle as well as its activity was rejected because the research records the native activity sequence and the lifecycle carried by a fault as unresolved; keying the copy on the activity alone, with suspended as the single lifecycle special case, keeps the mapping total over values the Dart event type already permits. Adding a member to the example session interface so the controller could ask the session whether it is capturing was rejected because the test fake implements that interface exactly, and the research lists leaving it alone as a constraint. The controller already knows whether its own start call succeeded, so the flag belongs to the controller.

## Steps

1. Add the two public fields and the private capture flag to `VoiceScreenController` in `example/lib/voice_screen_controller.dart`, with idle, false and false as their initial values. Complete when the controller exposes the displayed activity and the paused flag and both are readable from a test without any other change in behaviour.

2. Add the private copy mapping in the same file: one fixed English sentence per activity value, the suspended sentence, and one short label per activity value plus the paused label. The sentences and labels are the ones fixed under shared decisions below. Complete when every activity value the event type allows has a sentence and a label, with no fallthrough that could produce an enum name.

3. Reshape the shared session runner in the same file so each of the three wrappers can run its own success step on the successful in-epoch same-session path, and confirm by reading the code that the stale-completion branch still returns before any status assignment. Complete when Start, Interrupt and Stop each own their success behaviour and the stale Start path writes nothing.

4. Implement the Start, Interrupt and Stop success behaviour and the failure behaviour in the same file, as described in the approach. Complete when a successful Start produces the listening sentence with the capture flag set, a successful Interrupt produces the listening sentence without touching the capture flag, and a successful Stop produces the stopped sentence with the capture flag cleared.

5. Clear the capture flag, reset the displayed activity to idle and clear the paused flag on the background path, on the session teardown helper, on controller close, and on the subscription error path in the same file. Complete when no path that ends or abandons a session leaves the indicator claiming an active turn.

6. Rewrite the agent event handler in the same file to the capture-gated rules in the approach, removing the raw lifecycle-and-activity assignment entirely. Complete when no assignment in the file concatenates an enum name into the status, and an event that arrives while the capture flag is false changes neither the status, the displayed activity nor the paused flag.

7. Add the activity indicator to the conversation controls in `example/lib/main.dart`, keyed `activity-indicator`, inside the existing wrap, with an icon, the short label and a semantics label. Complete when the indicator renders beside the three unchanged buttons, the status text still sits in the live region, and no static sentence named below has moved or changed.

8. Write the controller tests in `example/test/voice_screen_controller_test.dart` and the widget test additions in `example/test/voice_screen_test.dart`, covering every acceptance criterion with its positive and negative case, including the two required negative cases: an event delivered before Start succeeds leaves the setup status unchanged, and a listening event never yields a status containing a lifecycle name, a middle dot and an activity name. Complete when both suites pass.

9. Run the repository checks and paste their output. Complete when formatting, analysis, the example test suite and the wiki linter are all clean with the output recorded.

## Interfaces and shared decisions

These decisions are fixed for every step. They were settled before implementation and cannot be renegotiated without a new validation round.

The three buttons stay three buttons. The Start control stays a filled button keyed `start-button`, disabled before setup, enabled when the controller can start and no operation is busy. Interrupt and Stop keep their keys and stay enabled when a session exists and no operation is busy. Nothing is added to the `ExampleVoiceSession` interface and nothing under `lib/` changes.

The controller gains a public `displayedActivity` field of type `TurnActivity` defaulting to idle, and a public `activityPaused` boolean defaulting to false. The capture flag stays private to the controller. The screen reads the two public fields; tests may read them too.

The capture flag becomes true only after the session's start call returns without throwing, while the epoch captured before the call is still current and the session field still holds the same object. It becomes false when Stop completes in-epoch on the same session, when the app goes to the background, when the session is torn down or the controller is closed, when a fault event arrives, when the subscription reports a stream error, and when an event reports a suspended lifecycle. Interrupt does not clear it.

While the capture flag is true, a non-fault event sets the status from the event's activity using the sentences fixed below and sets `displayedActivity` to that activity, except that a suspended lifecycle instead clears the capture flag, sets `displayedActivity` to idle, sets `activityPaused` to true and writes the paused sentence. While the capture flag is false, a non-fault event must not replace the status, and `displayedActivity` stays idle. During an in-flight Start, before success, `displayedActivity` also stays idle.

The fixed sentences while capture is true are: for listening, Listening. Say “hello”, “what is your name?”, or “thank you”. For recognizing, Hearing you. For thinking, Preparing a reply. For speaking, Speaking the reply. Listening is paused. For interrupting, Interrupting. For idle, Waiting for speech. The suspended sentence is: Paused by the system. Tap Start when you want to continue.

The successful in-epoch Start path writes the listening sentence above and sets `displayedActivity` to listening. The successful in-epoch Interrupt path writes that same listening sentence and sets `displayedActivity` to listening; neither the copy nor the label may claim that the microphone is listening while a reply is being spoken. The stale Start path that already stops a session abandoned by a background event returns before any status assignment. The stop success sentence stays: Stopped. Tap Start when you want to continue. The background sentence stays: Stopped while the app is in the background. The resume sentence stays: Ready. Tap Start when you want to continue.

The fault sentence stays exactly: The on-device speech engine reported a problem. Stop and retry. A fault also moves the phase to failed, sets `displayedActivity` to idle, clears `activityPaused` and clears the capture flag. Fault handling is unconditional and does not consult the capture flag, which preserves today's behaviour for faults.

`activityPaused` is set true only together with the suspended sentence, and is cleared by every other status write this feature owns: Start success and failure, Interrupt success and failure, Stop success and failure, the background write, the fault write, every activity-driven write, and the session teardown reset. Setup-phase status writes outside this feature are not touched.

The indicator is keyed `activity-indicator`, sits inside the existing conversation controls beside the three buttons, and renders an icon together with a text label and a semantics label carrying the same words, so the state is never signalled by colour alone. The label is the word Paused when `activityPaused` is true; otherwise it is the short label for `displayedActivity`: Idle for idle, Listening for listening, Hearing you for recognizing, Preparing a reply for thinking, Speaking for speaking, Interrupting for interrupting. The Idle label therefore covers the state before Start and after Stop.

Copy is English only. The words full duplex, barge-in and wake word do not appear, and no quality, accuracy or production-readiness claim is made. The static sentences that mention an English voice model, Files, sources, and licenses, Three English options, VCTK is a speaker choice, fixed demo rules, and listening pausing while a reply plays all stay in place, and the status text stays inside its live region. The substrings Not enough free space, background and Ready stay on the paths that already produce them.

One implementer owns all four touched files, because the behaviour and its tests overlap across them. No part of this work fans out.

## Risks

| Risk | Likelihood | Impact | Mitigation | Trigger that means it happened |
|---|---|---|---|---|
| Reshaping the shared session runner moves a status write ahead of the stale-completion branch, so a late Start result overwrites the background or stopped message. | Medium | High: two existing controller tests regress and the app lies about having stopped. | Keep the stale branch first and keep its early return; step 3 ends with a read of that branch, and the suite asserts the background and Ready substrings. | A controller test asserting the background substring or the Ready substring fails. |
| The capture flag is set on a stale Start, so events keep writing activity text after the app has left the foreground. | Medium | High: the UI claims a live turn while nothing is capturing. | Set the flag only inside the guarded success path, behind the existing epoch and session-identity checks, never in the wrapper before the call. | An event delivered after a background event changes the status. |
| A new activity value is added to the library enum later and the mapping has no sentence for it, reintroducing an enum name or an empty status. | Low | Medium: the defect returns silently. | Map every value exhaustively with no default branch, so a new value becomes a compile-time gap rather than a runtime string. | Analysis reports a non-exhaustive mapping, or a status renders an enum name. |
| The indicator is added as a replacement for a button rather than beside them, or changes the Start widget type. | Low | High: the widget test that reads a filled Start button fails and the explicit interrupt control disappears. | Add the indicator as an extra child of the existing wrap and change nothing about the three buttons. | The widget test asserting a disabled filled Start button fails, or Interrupt is absent. |
| New copy drifts into a capability claim, for example implying the microphone still listens during a reply or after a system pause. | Medium | Medium: the example contradicts the product's honesty limits. | Use the fixed sentences above verbatim; the speaking sentence states that listening is paused and the suspended sentence tells the user to tap Start. | A reviewer finds a forbidden term or a sentence that implies listening during speech. |

## Rollback

The change is confined to two example source files and two example test files, adds no dependency, no asset and no public library surface, and persists nothing. Reverting the commit restores the previous status behaviour, including the raw enum string, and removes the indicator; nothing else in the repository needs to be undone because no stored selection, no model file and no platform code is involved. A partial rollback is also available: removing the indicator from `example/lib/main.dart` leaves the controller's sentences working, since the indicator only reads fields it does not own.

## Out of scope

Any change under `lib/`, including making the library publish an event when start succeeds. Any change to the `ExampleVoiceSession` interface or to the test fake's member list. Replacing or merging the Start, Interrupt and Stop controls. Reading or changing native or web code to establish the real activity sequence; the two unresolved research questions stay unresolved and the mapping covers every value the Dart event type already allows. Colour, theme or layout redesign of the example beyond inserting one indicator. Localisation of any kind. Edits to `README.md`, `doc/capabilities.md` or the wiki product pages; wiki documentation is the later document phase, not an implementation task. Any claim about full duplex, barge-in, wake word, background listening, measured quality or production readiness.

## Verification approach

Every criterion in `02-criteria.md` is checked by a test in one of the two example test files, or by reading a named file, and each has a negative case recorded alongside it.

Controller behaviour is checked through the existing harness in `example/test/voice_screen_controller_test.dart`. The harness already drives initialize and download-and-prepare to a ready session, and the fake session already exposes an event stream, so a test adds an agent event to that stream after the controller has subscribed, which happens when the session is created during setup. Start, Interrupt and Stop are driven through the controller's own methods with the fake's start completer, which is also how the existing background and resume tests work, so the suspended, speaking, fault and ignored-event paths are reachable without touching the fake's member list.

The two required negative cases are explicit tests. The first delivers an event while the capture flag is still false, immediately after setup and before Start succeeds, and asserts that the status still contains the setup text and that `displayedActivity` is idle. The second delivers a listening event while capture is true and asserts that the resulting status contains the listening sentence and does not contain a lifecycle name followed by a middle dot and an activity name, which is the exact shape of the string being removed.

Preservation is checked by keeping the existing assertions: the Not enough free space substring on the insufficient-space path, the background substring on the late-Start-after-background path, and the Ready substring on the resume path. Screen behaviour is checked in `example/test/voice_screen_test.dart`, which keeps its current assertions on the disabled filled Start button and the static copy, and gains assertions that the indicator exists with the expected label for a given displayed activity and paused flag. Wording limits are checked by searching the two example source files for the forbidden terms. Finally the repository checks are run and their output pasted: formatting over `lib` and `example/lib`, analysis with infos and warnings fatal, the example test suite, and the wiki linter.
